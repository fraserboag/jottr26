# Space rollout and manual testing

## Before deployment

Use the usual `supabase/schema.sql` workflow for both existing and fresh databases. It includes space ordering, the `move_page_tree` function needed to sync note transfers between spaces, removal of the retired space colour column, and individual note recovery from deleted spaces. No separate migration file is required.

1. Open the Supabase SQL editor for the development/staging project your test app connects to.
2. Paste and run the **entire current** `supabase/schema.sql`, including its opening `begin;` and final `commit;`.
3. Refresh the app and retry sync if it previously failed. Drag a note into another space, wait for sync, and confirm the move on another device or browser.

Missing database support can cause sync errors or moves that do not persist across devices. Cursor/drop-indicator flicker is a separate UI issue. The incremental files in `supabase/migrations/` are an optional alternative for databases that already have the original space schema; do not run them in addition to the full schema. If ordering and transfers are already installed, `20261013000300_remove_workspace_colour.sql` removes the retired colour column and `20261013000400_restore_workspace_notes_individually.sql` installs individual note recovery. The client also cleans up saved local colour metadata when opening an existing account, preserving pending names and ordering.

Apply the entire updated `supabase/schema.sql` in the Supabase SQL editor before deploying the client. It runs as one transaction, creates space tables, migrates every existing account's live, trashed and permanently deleted page records into its stable Pages space, installs space lifecycle RPCs and publishes space metadata to realtime. Re-running it preserves renamed/deleted spaces and existing page membership. During backfill it temporarily removes the tombstone update trigger and recreates it before commit; a failed transaction also restores the original trigger.

The schema has not been applied to a live database by this task. SQL permissions, triggers, RPCs and concurrent operations need verification against a development Supabase project. README's default environment points to production, so use a development project for destructive recovery/purge checks.

`supabase/tests/workspaces-schema.sql` provides a focused SQL regression check after applying the schema. It uses temporary copies of the table shapes and the installed trigger logic, reproduces the old tombstone backfill failure, and checks migration protection plus legacy root/child creation and metadata upserts. It ends with ROLLBACK and never writes to real note tables. This check still needs running in PostgreSQL; no local PostgreSQL executable is available in this space.

The existing offline app upgrade mechanism adopts a new client build. Legacy writes that omit space membership retain it for existing pages and inherit it for children. New legacy roots use Pages while it is active, or another active space if Pages was deleted. Explicit space membership from the new client still respects space deletion/purge. Existing document and purge RPC signatures remain compatible with the old client.

The schema is designed to support the current production app before the frontend upgrade, but production compatibility has not been verified against a live database. An old cached client shows notes from all spaces together and cannot provide separation or restore a deleted space. Deploy the schema, manually check the existing production app's note creation/editing, nesting, sync and Trash, then deploy the new frontend before using space management. DDL takes table locks and can briefly delay writes while the migration commits. Verify the transition of cached clients as part of rollout.

## Manual checks

1. Open an existing account. It should still show PAGES without an arrow. Confirm the same note links, nested notes, order, favourites and Trash. A new account should receive the existing welcome note in Pages.
2. In Settings, create Work. Confirm the heading now has a space dropdown. Rename Pages to Personal. Try empty and duplicate names. Check that the Spaces heading matches Settings and that Inline spaces uses the same segmented style as Theme. Confirm there are no space colour controls or sidebar colour bars, including for previously coloured spaces, in both display modes after refreshing. Check light and dark themes, a narrow phone layout, and keyboard operation (Tab, arrow keys, Enter, Escape).
3. Switch between Personal and Work. Create roots and subpages in each. Each space should show only its own notes and favourites, and remember its last open page. Existing links and browser Back/Forward should reveal the owning space. Test the link picker in both modes.
4. Enable Inline spaces. Confirm separate sections and Add new actions, no empty-space message, and one uninterrupted Favourites list without space labels. Drag a note with children to another space's heading/Add new area, then try before/after/inside another note. Confirm the entire subtree moves with its IDs, content and favourites intact, while already-trashed descendants stay trashed. Drag space headings to reorder the sections, then reorder again using the Settings handles. Refresh and check another device for the same order. Focus a handle and try Up/Down keys. Disable inline mode and confirm the dropdown uses that order too. Check a second tab and a different account on the same device for preference isolation.
5. Trash a note in Work, then delete Work from Settings. Work should disappear from the active list. Its notes should appear in the normal Trash list while Personal is selected, with space names and no Deleted spaces section.
6. Restore a nested note from deleted Work. Work should return with only that note; its parent, children and other notes remain trashed. Select Work (or enable inline mode) and restore another note: only that note should join the space. A restored note whose parent remains trashed appears at the root. Check a reused space name prompts for a new name.
7. With multiple active spaces, Empty trash should delete the displayed list: the selected space's trash (all active spaces in inline mode) plus notes in deleted spaces. Check the item count matches the list, the confirmation appears, and an empty deleted space does not prevent the empty state. Last-active-space deletion should be disabled.
8. On two devices, keep one offline while creating/editing notes in Work. Delete Work on the other, then reconnect. Late notes and content must remain recoverable in Trash without reactivating Work. Restore one note and verify both devices show only that restored note in Work. Restore further notes individually and verify convergence. Also check competing space deletions leave at least one active space.
9. Repeat the sidebar, Settings, mode switch and recovery checks on a phone, including the keyboard and sidebar drawer. Use keyboard navigation to select spaces and operate settings.
10. On a narrow phone (320px width), confirm the Show all spaces simultaneously control remains visible and usable. Use the up/down buttons in Settings to reorder spaces without dragging, then use a page's three-dot Move to space menu to transfer it and its children. Check both sidebar rows and subpage lists, and verify the move on another device.
11. Select Work, follow a link to a Personal note, then open Trash or close the note. The selected space and Trash scope must remain Personal. Repeat with browser Back/Forward and inline spaces enabled.
12. On two offline devices, create spaces with the same name and add notes. Reconnect both: the conflicting space gets a numbered suffix, both sets of notes upload, and Settings explains the automatic rename. Repeat with conflicting renames and an 80-character name; confirm unrelated note edits continue syncing.

## Automated verification scope

Focused space tests cover local migration, membership, synced space ordering, unsynced and complete-subtree transfers, name validation, individual space recovery/provenance, scoped Trash, purge queuing, two-device sync and retry/rejection handling. The fake Supabase server checks the client protocol; it does not replace validation of the actual SQL functions and RLS policies.

Type checking and lint are lightweight checks. No browser automation, end-to-end suite, broad test suite or production build is required for this handoff. Wait for manual feedback before further testing or iteration.
